    Upstream DNS

    —

    Where Unbound sends queries that miss the cache and local records. Recursive resolves directly from the root servers (default — no third party sees your queries). Forwarding sends everything to the chosen provider; Quad9 and OpenDNS add their own malware/domain filtering on top of your Unbound blocklists. Saves go through the same path as the System → DNS form: a backup of router-dns.conf is made first, listen addresses/port/protocols are preserved, and Unbound hot-reloads (no downtime). If unbound-checkconf rejects the config the backup is restored automatically.

    Pi-hole / custom server
    Your own LAN DNS server — queries chain through it

    DNS-over-TLS encrypts router→upstream queries (port 853, authenticated server certs). Providers carrying the green TLS tag support it (AdGuard, CleanBrowsing, Cloudflare, OpenDNS, Quad9, Google — all verified reachable with valid certs from this router); untagged providers (Comodo, Control D, DNS.Watch) and Pi-hole/custom use plaintext port 53. Mullvad is marked shutting down — its public DNS service goes offline November 2, 2026, so don't pick it for new setups. TLS also requires the Encrypt upstream checkbox — the tag alone only marks support. LAN clients still query the router over plaintext 53 — DoT covers only the upstream hop.

    DMZ Clients
    
            Isolate a client from the LAN while keeping it reachable from the internet.
          
    
          
    
            ⚠
            
    
              Soft DMZ — iptables isolation
    
              DMZ clients share the LAN subnet. Isolation is enforced by FORWARD DROP rules
              that block the DMZ client from initiating connections to any other LAN host.
              The DMZ client can still reach the gateway (DNS / management) and the internet.
              A static DHCP reservation is required so port forwards always
              reach the correct host.

    Honeypot 
    
            
          
    
          
        
    
        
    
          
          
    
            
            Auto-ban
          
    
          
          hits → ban
          
        
    
        
    
        
    
          
    
            
    StatusIPPortHeldFirst seen
    
            
          
    
        
    
        
    A port-garden tarpit: classic scan ports (telnet, RDP, SMB, adb…) are bound on the WAN addresses only (IPv4 + IPv6) — every connection is held open with a clamped TCP window while the scanner waits forever for data that never comes. Any connection here is hostile by definition, so sources are auto-banned via CrowdSec (1 year) — no manual banning, no AbuseIPDB cross-checking needed, and the catch is shared with the community list above. LAN/WireGuard sources are closed immediately and never counted. Overflow connections beyond the safety caps (256 total / 8 per IP) are dropped, not trapped, so a botnet flood can't exhaust the router. Keep the threshold at 1: nothing legitimate ever connects to these ports, so a single completed handshake is hostile by definition — only raise it (to 3–5) if you add a port that could plausibly see innocent traffic (e.g. 80/443).

    The OpenCanary deception emulators — SSH, VNC, MSSQL, Redis, SNMP — bound on the WAN address only, running as a sandboxed service user. Any interaction is hostile by definition (nothing legitimate connects to services that do not exist), so sources are auto-banned via CrowdSec (1 year) and the catch is shared with the community list above. The full record lives at /var/log/opencanary/opencanary.log.

          Automatic mode (recommended) — enabling it bans all IP addresses in the community ban list: every entry is deception-verified (a canary/honeypot catch on a real TuxWall), so automatic blocking carries near-zero false-positive risk.
